FEA Future Features — Implementation Plan

Features a basic 3D frame analysis program is expected to have that the fea module does not provide yet, each with a proposed API, an implementation approach, its tests and its effort, in the order they should be built.

Overview

The module already analyses 3D frames for user-defined load cases and combinations, with nodal, uniform, point and self-weight loads, end releases, springs, member diagrams with deflections, envelopes, design demands, input validation with located errors, a banded solver and ESM/CJS builds. This plan covers what is still missing for a frontend frame-analysis program. Nothing on this page is implemented.

Phase 1
Needed before the UI design is frozen: they shape input forms and result screens.
Phase 2
Common load and modelling options that slot into existing screens.
Phase 3
Larger changes to the solver: building diaphragms and shear deformation.
ℹ️ Effort is relative: S ≈ a day, M ≈ a few days, L ≈ a week or more, each including tests and docs.

Rules for every feature

These follow from the current architecture and AGENTS.md; each feature below assumes them.

1
Linear in the loads. Any new result must be linear in the loads, or load combinations (superposition of raw states) break. Nothing here is nonlinear.
2
Validated with a location. Every new input field is checked in validation/validate-model.ts (finite numbers, allowed options, references) and reported with details naming the node, member, load case or field.
3
No dense global matrix. New stiffness terms are added to the skyline profile; anything that couples many DOFs (diaphragms) must keep the band narrow.
4
Units as today: mm, MPa, kN, kN·m, kN/m, rad; new quantities state theirs (°C, 1/°C, kN/m³).
5
Verified against hand-calculated or textbook values, and where possible against an independent model (e.g. a subdivided member) — the pattern used for deflections and combinations today.
6
Documented in the same change: html-docs/fea/index.html with values from real runs, the landing page, and the README.
Sections & materials fea/sections/

Today only rectangular RC sections have a helper (rectBeamToSectionProperties in rc); any other section needs hand-computed E, G, A, I22, I33, J. A section editor needs builders for the common shapes and material presets.

FN frameSection(shape, material) Planned Section geometry

Builds SectionProperties from a shape and a material. Local 2 is the depth direction, as in the rest of the module, so I33 is the major axis.

Parameters
ParamTypeUnitRequired?Description
shapeSectionShapemmRequiredOne of { kind: "rectangle", b, h }, { kind: "circle", d }, { kind: "pipe", d, t }, { kind: "box", b, h, tf, tw }, { kind: "i", d, bf, tf, tw } (doubly symmetric I/H), { kind: "tee", d, bf, tf, tw }
materialFrameMaterialMPa, kN/m³Required{ E, nu, unitWeight, alpha? }; from a preset below or user-defined
Example
TypeScript (proposed)
const beam = frameSection(
  { kind: "i", d: 400, bf: 200, tf: 13, tw: 8 },  // mm
  steelMaterial(),                               // E 200 000 MPa, ν 0.3, γ 78.5 kN/m³
);
const column = frameSection({ kind: "rectangle", b: 400, h: 400 }, concreteMaterial(32));  // f′c, MPa
Returns

{ sectionProperties, calculationDetails: { shape, Asy?, Asz?, ... }, unit, warnings } — the repo's return shape; the shear areas Asy, Asz are computed now so shear deformation (Phase 3) needs no new input.

Implementation
QuantityBasis
A, I22, I33Exact formulas for each shape (parallel-axis theorem for the tee's centroid)
J, solidRectangle: existing formula; circle πd⁴/32
J, thin-walled closedBredt: 4Am²/∮(ds/t) for box and pipe
J, thin-walled openΣ b·t³/3 for I and tee (warping torsion ignored — document it)
GE / (2(1 + ν))
⚠️ Pushes a warning when a thin-walled formula is used outside its range (e.g. t > d/10) — Section geometry, thin-walled assumption.
⚠️ Throws FrameAnalysisError 314 with details.field for non-finite or non-positive dimensions, and 315 for inconsistent shapes (e.g. 2·tf ≥ d).
FN concreteMaterial(fc_, options?) · steelMaterial(options?) Planned

Material presets: concrete E = 4700√f′c (existing concreteElasticModulus), ν = 0.2, γ = 24 kN/m³, α = 1.0·10⁻⁵ /°C; structural steel E = 200 000 MPa, ν = 0.3, γ = 78.5 kN/m³, α = 1.2·10⁻⁵ /°C. Every value can be overridden.

ℹ️ Keep rectBeamToSectionProperties as the RC entry point (it applies the ACI cracked-section modifiers); it can call the rectangle builder internally.
Tests

Each shape against published section tables (e.g. a hot-rolled I-shape's A, I and J from a steel manual, citing the source), the tee centroid by hand, thin-wall J against the exact solid value for a thick and a thin case, and the presets' values.

Truss members

Axial-only members are possible today by releasing moments at both ends and torsion at one, but a UI needs a simple toggle, and a node connected only by truss members then has free rotations — a mechanism (304) the user did not cause.

TYPE Member.type?: "frame" | "truss" Planned

A "truss" member gets only the axial terms of the stiffness (EA/L) and carries only N.

Implementation
1
Element: a 12×12 matrix with only the axial terms; member loads still allowed, with their transverse part sent straight to the end nodes as simply supported reactions.
2
Rotation stabilising: rotational DOFs of nodes connected only by truss members (and with no rotational restraint or nodal moment) are fixed automatically, and listed in calculationDetails.autoRestrainedDofs so the UI can show it.
3
Diagrams: N only (V, M, T zero); deflection between nodes is the straight line plus the transverse load's simply supported sag.
⚠️ Throws 314 (field: "type") for another value, and 307 if a truss member also has releases.
Tests

A pin-jointed plane truss against the method of joints; the same truss built from frame members with releases (oracle); a 3D space truss against a textbook example.

Varying member loads

Triangular and trapezoidal loads — soil and water pressure, slab tributary loads on beams — can only be approximated today with several partial uniform loads.

TYPE { type: "trapezoid", w1, w2, start?, end? } Planned

A load varying linearly from w1 at start to w2 at end (kN/m), in any direction; a triangle is w1 = 0.

TypeScript (proposed)
{ loadCase: "SD", type: "trapezoid", memberId: "B12", direction: "Z",
  w1: 0, w2: -12, start: 0, end: 2500 }  // kN/m, mm
Implementation
1
Fixed-end forces: the existing shape-function integral with a linear load; the 4-point Gauss rule is exact up to degree 7, so it stays exact.
2
Diagrams: closed-form resultant and first moment of a linear load in internalForces; M becomes cubic and the deflection integrand quartic, so one Simpson panel per interval is no longer exact — use 3-point Gauss per interval.
Tests

Fixed–fixed triangular load: end moments wL²/30 and wL²/20; simply supported triangle: Mmax = wL²/(9√3) at L/√3; deflection against the subdivided-member oracle; a trapezoid equal to a uniform plus a triangle.

Member point moments
TYPE { type: "moment", direction, M, a } Planned

A concentrated moment M (kN·m) about the given axis at distance a. Today it requires splitting the member and applying a nodal moment.

Implementation

Fixed-end forces from the derivatives of the beam shape functions at a; in the diagrams, a jump of M at a (both sides reported, as for shear at a point load). Axis "1" is a torque.

Tests

Fixed–fixed beam with a moment at midspan (end moments M/4) and at a general position; the subdivided-member oracle with a nodal moment.

Envelope sets

The envelope covers every combination today; users expect named groups such as "Strength" and "Service".

TYPE FrameModel.envelopes?: { id, combinations }[] Planned
TypeScript (proposed)
envelopes: [
  { id: "STRENGTH", combinations: ["1.4D", "1.2D+1.6L", "0.9D+1.0W"] },
  { id: "SERVICE",  combinations: ["D+L"] },
]
// result.envelopes.STRENGTH, result.envelopes.SERVICE; result.envelope stays "all combinations"
memberDemandEnvelope(result, "B12", { envelope: "STRENGTH" });
Implementation

Reuse buildEnvelope per set. Validate ids (unique across cases, combinations and envelopes; 303) and references (309).

Tests

Each set's governing ids; a set of one combination equals that combination; unknown references.

Local axes & schemaVersion
TYPE FrameResult.members: { memberId, length, axes }[] Planned

Each member's length and local axes (the rows of λ) in the result, so the UI can offset diagrams perpendicular to members without recomputing memberAxes.

FN FrameModel.schemaVersion · migrateFrameModel(model) Planned

A version number on the model, so saved project files keep working as the model format grows. migrateFrameModel upgrades an older model step by step; validateFrameModel reports a version newer than the library (314, field: "schemaVersion").

Tests

A model without a version is treated as version 1; each migration step on a fixture file; round trip through JSON.

Projected loads
TYPE udl / trapezoid: projected?: boolean Planned

For a global-direction load, projected: true means "per unit length of the member's projection perpendicular to the load direction" (snow on a rafter is per horizontal length). The load per member length is w · (projected length / L).

Tests

A rafter at 30°: total load w·L·cos 30°; a vertical member gets no load from a projected vertical load; rejected (314) on a local direction.

Support settlement
TYPE FrameModel.supportDisplacements?: { loadCase, nodeId, ux…rz }[] Planned

An imposed displacement (mm) or rotation (rad) at a fixed DOF, belonging to a load case like any load.

Implementation

For prescribed values ur at fixed DOFs: F_free −= K_fr · u_r, assembled member by member (no dense K); after the solve, the full U includes ur, so end forces and reactions follow unchanged. Linear, so it combines like any case.

⚠️ 316 if the DOF is not fixed (a spring or free DOF cannot take an imposed displacement).
Tests

Fixed–fixed beam with end settlement Δ: end moments 6EIΔ/L², shear 12EIΔ/L³; propped cantilever settlement 3EIΔ/L²; two-span beam middle-support settlement against a textbook table.

Temperature loads
TYPE { type: "temperature", deltaT?, gradient2?, gradient3? } Planned

A uniform temperature change deltaT (°C) and linear gradients across the depth in local 2 and 3 (°C/mm). Needs a thermal coefficient alpha (1/°C) on the section (from the material presets).

Implementation

Fixed-end forces: axial E·A·α·ΔT, moments E·I·α·gradient; diagrams subtract the free thermal strain/curvature so deflections are correct for a free member.

⚠️ 313-style error (new code 317) if a temperature load is applied to a member without alpha.
Tests

A fixed–fixed bar: N = −EAαΔT and no displacement; a free cantilever: elongation αΔTL and tip deflection from a gradient αgL²/2 with no forces.

End offsets (rigid zones)
TYPE Member.endOffsets?: { start?, end?, rigidZoneFactor? } Planned

Lengths (mm) at each end, along the member, treated as rigid — e.g. the half-depth of the column a beam frames into — so the flexible length and the reported face moments are realistic. rigidZoneFactor (0–1, default 1) makes only part of the offset rigid, as in ETABS.

Implementation

A rigid-link transformation between the node and the flexible end, applied to the stiffness and to the fixed-end forces; loads on the rigid zones go straight to the node. Diagrams cover the flexible length and report the face forces; memberDemandEnvelope uses the faces.

Tests

A beam with offsets equals a shorter beam between rigid links built from very stiff members (oracle); face moments of a portal frame with joint zones.

Rigid floor diaphragms

Building floors are stiff in their plane. Without a diaphragm constraint, lateral analysis of a building either ignores the slab or needs fake bracing.

TYPE FrameModel.diaphragms?: { id, nodeIds }[] Planned

Nodes of one floor that move together in the horizontal plane: each keeps its own UZ, RX, RY, while UX, UY, RZ follow a master point at the floor's centroid.

Implementation
1
Constraint: for a slave node at (x, y) and master at (xm, ym): ux = Ux − (y − ym)·Rz, uy = Uy + (x − xm)·Rz, rz = Rz. Eliminate the slave DOFs by transforming each member's stiffness and load vector.
2
Band: the three master DOFs couple every node of the floor. Number them right after their floor's nodes in the RCM order so the skyline band stays about one floor wide.
3
Results: diaphragm displacements and rotations, story drift between floors, and in-plane forces in members are no longer meaningful within the diaphragm (document it).
⚠️ 318 for a node in two diaphragms, or a diaphragm node with a fixed in-plane DOF.
Tests

A one-storey frame with a diaphragm equals the same frame with very stiff horizontal bracing (oracle); torsion of an eccentric floor; band size stays close to the no-diaphragm model.

Shear deformation (Timoshenko)
TYPE SectionProperties.Asy?, Asz? · AnalyzeFrameOptions.shearDeformation? Planned

Shear areas from the section builders and an option to include shear flexibility, which matters for deep beams and short columns. Today the element is Euler–Bernoulli.

Implementation

The standard Timoshenko 12×12 matrix with Φ = 12EI/(G·As·L²), consistent fixed-end forces and diagram deflections with the shear term. The reference matrix stays the default (Φ = 0) so existing results do not change.

Tests

Cantilever tip deflection PL³/3EI + PL/(G·As); with large As it equals the Euler–Bernoulli result.
