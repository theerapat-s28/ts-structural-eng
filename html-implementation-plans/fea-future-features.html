FEA Future Features — Implementation Plan

Features a basic 3D frame analysis program is expected to have that the fea module does not provide yet, each with a proposed API, an implementation approach, its tests and its effort, in the order they should be built.

Overview

The module already analyses 3D frames for user-defined load cases and combinations, with nodal, uniform, trapezoidal, point, torque and self-weight loads, area loads on null areas, end releases, springs, member diagrams with deflections, envelopes, design demands, input validation with located errors, a banded solver and ESM/CJS builds. This plan covers what is still missing from it as a structural analysis engine. Features finished since it was first written are listed under Delivered; nothing else on this page is implemented yet.

Delivered
Varying member loads, distributed torque and null areas (area loads to beams).
Phase 1
Core modelling inputs and results: sections, loads, releases and envelopes most models need.
Phase 2
Common load and modelling options that extend the existing model format.
Phase 3
Larger changes to the solver: building diaphragms and shear deformation.
ℹ️ Effort is relative: S ≈ a day, M ≈ a few days, L ≈ a week or more, each including tests and docs.
ℹ️ Engine only. The library is the analysis engine that front-end applications install. Drawing, member colours, display options and other UI concerns belong to those applications, so nothing on this page plans for them.

Rules for every feature

These follow from the current architecture and AGENTS.md; each feature below assumes them.

1
Linear in the loads. Any new result must be linear in the loads, or load combinations (superposition of raw states) break. Nothing here is nonlinear.
2
Validated with a location. Every new input field is checked in validation/validate-model.ts (finite numbers, allowed options, references) and reported with details naming the node, member, load case or field.
3
No dense global matrix. New stiffness terms are added to the skyline profile; anything that couples many DOFs (diaphragms) must keep the band narrow.
4
Units as today: mm, MPa, kN, kN·m, kN/m, rad; new quantities state theirs (°C, 1/°C, kN/m³).
5
Verified against hand-calculated or textbook values, and where possible against an independent model (e.g. a subdivided member) — the pattern used for deflections and combinations today.
6
Documented in the same change: html-docs/fea/index.html with values from real runs, the landing page, and the README.
7
Analysis data only. Inputs and results carry structural quantities, never presentation data (colours, labels for display, view state); the front-end derives what it draws from them.

Decisions taken

No area self-weight (users apply slab weight as a dead area load); loads per true area (projected later); a missing edge member is an error; one-way strips may not land on an unsupported edge; cantilevers are constant-depth rectangles. The relaxations are collected under Null area extensions.

ℹ️ The API reference also gained a card for every exported type (43, including MemberDiagram and MemberStation), which the earlier docs lacked.
Area geometry tolerance core/constants

Found in review. Every null-area check uses one relative tolerance, AREA_GEOMETRY_TOLERANCE = 10⁻⁶ times the longest edge — 0.006 mm on a 6 m bay. Measured on a 6 m × 4 m bay: a node 0.01 mm off the beam line breaks the edge chain (316), and a corner 0.5 mm out of plane is rejected (315). Coordinates from a drawing, a CAD import or rounding will fail where an engineer would see no problem.

CONST AREA_LENGTH_TOLERANCE · AREA_ANGLE_TOLERANCE Planned

Split the single relative value into the two things it is used for, sized for real-world coordinates.

CheckToleranceProposed
Planarity, node on an edgelengthAn absolute length, e.g. 1 mm — well below construction tolerance
Parallel edges, square corners, convexityangleAn angle, e.g. 10⁻³ rad (≈ 0.06°)
Degenerate area, repeated noderelativeKeep 10⁻⁶ × size: only true degeneracies
Implementation

Profiles are built in the area's plane, so a slightly warped quad is projected onto its best-fit plane and a near-edge node is projected onto the edge — the load still adds up to q·A. Consider an optional model-level override for imported models.

Tests

Offsets just inside and just outside each tolerance; totals still q·A for an accepted, slightly warped area; the existing geometry tests unchanged.

Sections & materials fea/sections/

Today only rectangular RC sections have a helper (rectBeamToSectionProperties in rc); any other section needs hand-computed E, G, A, I22, I33, J. The engine needs builders for the common shapes and material presets.

Axial-only members (end releases)

No separate truss element: an axial-only (pin-jointed) member stays an ordinary frame member with end releases — moments released at both ends and torsion at one end. The member forces are already right: a triangle truss built this way gives the method-of-joints values (3.333 kN tension, 6.009 kN compression under a 10 kN apex load). The gap is the joints: where every member meeting a node releases its rotations, the node's rotational DOFs have no stiffness, and the analysis throws 304 for a mechanism the user did not cause, unless they restrain those rotations by hand.

TYPE Member.releases — { start: { r1, r2, r3 }, end: { r2, r3 } } Planned

The existing MemberEndRelease flags, used as the axial-only pattern; the model format does not change.

TypeScript
{ id: "D1", startNodeId: 3, endNodeId: 7, section: brace,
  releases: {
    start: { r1: true, r2: true, r3: true },  // torsion released at one end only
    end:   { r2: true, r3: true },
  } }
Implementation
1
Rotation stabilising: before factorising, find the rotational DOFs whose assembled stiffness is exactly zero — every member at the node releases that rotation and no spring or restraint holds it — and fix them. They carry no force, so the results do not change. List them in calculationDetails.autoRestrainedDofs (node and DOF) so the caller can see what was restrained.
2
Keep real mechanisms: a DOF that also has a nodal moment applied in some load case is not fixed silently; it stays a 304 naming that node and DOF.
3
Docs: show the release pattern on the API page (Member and MemberEndRelease cards), why torsion is released at one end only (both ends is a rigid-body twist, 307), and that member loads on such a member still produce bending between its pinned ends.
⚠️ No new codes: 307 stays for torsion (or axial force) released at both ends, and 304 for a joint mechanism that stabilising cannot remove.
Tests

A pin-jointed plane truss built from released members, with no rotational restraints, against the method of joints; the same truss with rotations restrained by hand gives identical results (oracle); a 3D space truss against a textbook example; a nodal moment on a fully released joint still throws 304.

Member point moments
TYPE { type: "moment", direction, M, a } Planned

A concentrated moment M (kN·m) about the given axis at distance a. Today it requires splitting the member and applying a nodal moment. (A distributed torque about local 1 now exists as TorqueMemberLoad.)

Implementation

Fixed-end forces from the derivatives of the beam shape functions at a; in the diagrams, a jump of M at a (both sides reported, as for shear at a point load). Axis "1" is a torque, reusing the torsion shape functions added for TorqueMemberLoad. Build the moment terms so distributed moments can integrate them.

Tests

Fixed–fixed beam with a moment at midspan (end moments M/4) and at a general position; the subdivided-member oracle with a nodal moment.

Projected loads
TYPE udl / trapezoidal / AreaLoad: projected?: boolean Planned

For a global-direction load, projected: true means "per unit length of the member's projection perpendicular to the load direction" (snow on a rafter is per horizontal length). The load per member length is w · (projected length / L). On an AreaLoad with a global direction it means per unit plan area perpendicular to the load: the true-area load is q · |n · e|, a single factor per area, so the distribution itself is unchanged.

Tests

A rafter at 30°: total load w·L·cos 30°; a vertical member gets no load from a projected vertical load; a ramp area at θ: reactions q·A·cos θ; rejected (314) on a local direction or on "3".

Distributed member moments
TYPE { type: "distributedMoment", axis: "2" | "3", m, start?, end? } Planned

A moment per unit length (kN·m/m) about local 2 or 3. Needed so a cantilever null area can carry a load component along its support edge — today rejected with 317 because that component bends the beam in its own plane — and useful for eccentric line loads in general.

Implementation

Fixed-end forces by integrating the point-moment terms (from member point moments) over the loaded length; in the diagrams M gains a linear term and V is unaffected. Then the cantilever distribution emits the in-plane moment and validation drops that 317 case.

Tests

Fixed–fixed beam with a uniform distributed moment against the integrated point-moment solution; a cantilever area on a ramp whose support edge runs down the slope: statics equal to the area load.

Member twist
TYPE MemberStation.r1 · extremes.r1 Planned

The rotation about local 1 (rad) along a member. With torque loads — including every cantilever null area — the largest twist is between the nodes, where no result shows it today.

Implementation

φ′ = T / GJ integrated along the grid like u1, with the constant from the end rotations about local 1 (the released end skipped). Linear in the loads. Adds "r1" to StationComponent, so the envelope gains it too.

Tests

Fixed–fixed member, uniform torque: φmax = tL²/(8GJ) at midspan; cantilever: tip φ = tL²/(2GJ); end values equal the node rotations.

Support settlement
TYPE FrameModel.supportDisplacements?: { loadCase, nodeId, ux…rz }[] Planned

An imposed displacement (mm) or rotation (rad) at a fixed DOF, belonging to a load case like any load.

Implementation

For prescribed values ur at fixed DOFs: F_free −= K_fr · u_r, assembled member by member (no dense K); after the solve, the full U includes ur, so end forces and reactions follow unchanged. Linear, so it combines like any case.

⚠️ 319 if the DOF is not fixed (a spring or free DOF cannot take an imposed displacement).
Tests

Fixed–fixed beam with end settlement Δ: end moments 6EIΔ/L², shear 12EIΔ/L³; propped cantilever settlement 3EIΔ/L²; two-span beam middle-support settlement against a textbook table.

Temperature loads
TYPE { type: "temperature", deltaT?, gradient2?, gradient3? } Planned

A uniform temperature change deltaT (°C) and linear gradients across the depth in local 2 and 3 (°C/mm). Needs a thermal coefficient alpha (1/°C) on the section (from the material presets).

Implementation

Fixed-end forces: axial E·A·α·ΔT, moments E·I·α·gradient; diagrams subtract the free thermal strain/curvature so deflections are correct for a free member.

⚠️ 313-style error (new code 320) if a temperature load is applied to a member without alpha.
Tests

A fixed–fixed bar: N = −EAαΔT and no displacement; a free cantilever: elongation αΔTL and tip deflection from a gradient αgL²/2 with no forces.

End offsets (rigid zones)
TYPE Member.endOffsets?: { start?, end?, rigidZoneFactor? } Planned

Lengths (mm) at each end, along the member, treated as rigid — e.g. the half-depth of the column a beam frames into — so the flexible length and the reported face moments are realistic. rigidZoneFactor (0–1, default 1) makes only part of the offset rigid, as in ETABS.

Implementation

A rigid-link transformation between the node and the flexible end, applied to the stiffness and to the fixed-end forces; loads on the rigid zones go straight to the node. Diagrams cover the flexible length and report the face forces; memberDemandEnvelope uses the faces.

Tests

A beam with offsets equals a shorter beam between rigid links built from very stiff members (oracle); face moments of a portal frame with joint zones.

Rigid floor diaphragms

Building floors are stiff in their plane. Without a diaphragm constraint, lateral analysis of a building either ignores the slab or needs fake bracing.

TYPE FrameModel.diaphragms?: { id, nodeIds }[] Planned

Nodes of one floor that move together in the horizontal plane: each keeps its own UZ, RX, RY, while UX, UY, RZ follow a master point at the floor's centroid. Null areas already outline the floors, so a diaphragm id on NullArea (collecting the nodes of its areas) would define both at once; the areas themselves still add no stiffness.

Implementation
1
Constraint: for a slave node at (x, y) and master at (xm, ym): ux = Ux − (y − ym)·Rz, uy = Uy + (x − xm)·Rz, rz = Rz. Eliminate the slave DOFs by transforming each member's stiffness and load vector.
2
Band: the three master DOFs couple every node of the floor. Number them right after their floor's nodes in the RCM order so the skyline band stays about one floor wide.
3
Results: diaphragm displacements and rotations, story drift between floors, and in-plane forces in members are no longer meaningful within the diaphragm (document it).
⚠️ 321 for a node in two diaphragms, or a diaphragm node with a fixed in-plane DOF.
Tests

A one-storey frame with a diaphragm equals the same frame with very stiff horizontal bracing (oracle); torsion of an eccentric floor; band size stays close to the no-diaphragm model.

Shear deformation (Timoshenko)
TYPE SectionProperties.Asy?, Asz? · AnalyzeFrameOptions.shearDeformation? Planned

Shear areas from the section builders and an option to include shear flexibility, which matters for deep beams and short columns. Today the element is Euler–Bernoulli.

Implementation

The standard Timoshenko 12×12 matrix with Φ = 12EI/(G·As·L²), consistent fixed-end forces and diagram deflections with the shear term. The reference matrix stays the default (Φ = 0) so existing results do not change.

Tests

Cantilever tip deflection PL³/3EI + PL/(G·As); with large As it equals the Euler–Bernoulli result.
